# Ссылки на экраны In.Plan — инструкция

Как проставить переходы из карточек процесса в конкретные экраны In.Plan, чтобы их видели
все читатели вики, а не только вы.

Это главное, ради чего карта встраивается в вики: сама схема процесса есть и в презентации,
а вот перехода «из шага в рабочий экран» больше нигде нет.

## Где ссылки хранятся и почему именно там

У ссылки два возможных места, и разница принципиальная.

**`localStorage` браузера** — сюда пишет редактор, пока вы работаете. Ключ
`inplan-process-map:overrides:v1`. Это **черновик**: правки видны только в том браузере,
где их сделали. Читатель вики откроет карту и не увидит ни одной ссылки. Другой ваш
компьютер — тоже не увидит.

**`src/data/process.json`** — источник истины. Попадает в сборку, разворачивается на
GitHub Pages, виден всем. **Ссылки должны оказаться здесь.**

Редактор — это удобный способ набрать ссылки и выгрузить их одним файлом. Он не заменяет
коммит в репозиторий.

## Способ 1. Через редактор в браузере (рекомендуется)

Подходит, когда ссылок несколько и хочется видеть, к какому шагу их приставляешь.

### Шаг 1. Открыть карту и включить редактор

Открыть https://igordikinov.github.io/process-map/ (или локально `npm run dev`).

В тулбаре справа сверху переключить **«Просмотр» → «Редактор»**.

> Режим не сохраняется между сессиями: после перезагрузки карта всегда открывается
> в «Просмотре». Это сделано намеренно, чтобы читатель вики случайно не остался
> в редакторе (SPEC §4.4).

### Шаг 2. Проставить ссылки

1. Кликнуть по карточке этапа — откроется детализация.
2. Кликнуть по карточке шага — справа откроется панель.
3. В секции **«Экран в системе»** нажать **«Добавить»** (кнопка видна только в редакторе).
4. Заполнить:
   - **Название экрана** — как он называется в In.Plan, например
     `Планирование поставок › Объёмный план`. Не длиннее 80 символов, рядом счётчик.
   - **Ссылка** — полный URL, начиная с `https://`.
5. **Сохранить.**

Что проверяет форма:

| Ввод | Реакция |
|---|---|
| пустое поле названия | «Укажите название экрана», сохранение заблокировано |
| пустая ссылка | «Укажите ссылку на экран» |
| не URL | «Введите корректный URL» |
| `javascript:`, `data:`, `file:` | «Допустимы только ссылки https:// и http://» |
| `http://…` | «Ссылка без шифрования (http). Рекомендуется https» — **сохранить можно** |

Сразу после сохранения на карточке шага появится иконка внешней ссылки, а кнопка
«Открыть в модуле» в панели станет активной.

**Изменить или удалить** уже проставленную ссылку — та же секция, кнопка «Изменить»,
внутри формы слева «Удалить ссылку».

### Шаг 3. Выгрузить

В тулбаре редактора нажать **«Экспорт JSON»**. Скачается файл `process.json` —
это **полная карта** со всеми вашими ссылками, а не только правки.

### Шаг 4. Положить в репозиторий

```bash
# из папки со скачанным файлом
cp process.json C:/Git/process-map/src/data/process.json
cd C:/Git/process-map
git diff --stat src/data/process.json    # ожидается: только добавленные screen
npm run check                            # схема и целостность данных
git add src/data/process.json
git commit -m "feat(data): ссылки на экраны для этапа N"
git push
```

Файл экспорта **побайтово совпадает** по формату с файлом в репозитории — тот же отступ,
неэкранированная кириллица, LF, перевод строки в конце. Поэтому его можно класть поверх
без правок руками, и `git diff` покажет только добавленные строки `screen`.

### Шаг 5. Сбросить черновик

После того как ссылки уехали в репозиторий, черновик в браузере больше не нужен и будет
только сбивать с толку: карта покажет ваши локальные правки поверх коммита.

В тулбаре редактора — **«Сбросить правки»**.

> Действие необратимо и без подтверждения. Сначала убедитесь, что коммит на месте.

## Способ 2. Правкой JSON вручную

Подходит для массовой заливки, когда список «шаг → ссылка» уже готов, например в таблице.

Найти узел по `id` или по `label` и дописать поле `screen`:

```json
{
  "id": "sohranenie-predyduschih-versiy-planov",
  "type": "step",
  "label": "Сохранение предыдущих версий планов",
  "screen": {
    "title": "Планирование поставок › Версии планов",
    "url": "https://inplan.company.ru/screens/plan-versions"
  },
  "position": { "x": 710, "y": 110 }
}
```

**Порядок ключей важен.** `screen` ставится **до** `position` — так задан порядок
в zod-схеме, и на нём держится побайтовое совпадение с экспортом из приложения.
Порядок полей узла: `id`, `type`, `label`, `description`, `group`, `inputs`, `outputs`,
`system`, `owner`, `screen`, `position`.

После правки обязательно:

```bash
npm run check      # tsc + eslint + vitest: схема, целостность рёбер, ≥40 узлов
```

Если схема не сойдётся, тест упадёт с указанием узла — молча битые данные не пройдут.

## Что происходит после коммита

Push в `main` запускает `.github/workflows/deploy.yml`:

1. ставятся зависимости;
2. прогоняется `npm run check` — **если он красный, деплой не состоится**;
3. собирается `dist/`;
4. выкладывается на GitHub Pages.

Через минуту-две ссылки видны всем на https://igordikinov.github.io/process-map/

## Перегенерация данных из презентации

Когда меняется `SNP Е2Е процесс.pptx`, данные пересобираются. **Порядок обязателен:**

```bash
python scripts/import-pptx.py     # содержание процесса из презентации
npm run layout                    # координаты через dagre
npm run check
```

Почему именно так: импортёр записывает координаты из презентации, а они дают
157 пересекающихся пар узлов. `npm run layout` пересчитывает раскладку через dagre
и убирает пересечения. Если прогнать только импорт и закоммитить, карта отрисуется
кашей из наложенных карточек.

**Ссылки при этом сохраняются.** Импортёр читает предыдущий `process.json` и переносит
`screen` (а также `owner`) на узлы с совпадающими `id`. Отчёт печатает, что именно
перенесено:

```
РУЧНЫЕ ПОЛЯ (ссылки на экраны, ответственные) — ПЕРЕНОС ИЗ ПРЕДЫДУЩЕГО JSON
  узлов в предыдущем файле: 103
  перенесено ссылок (screen): 12
  потеряно ссылок (screen):   0
```

## Если узел исчез из презентации

Самый вероятный сценарий: шаг переформулировали, у него сменился `id`, и ссылка осталась
без хозяина.

Импортёр это **не замалчивает**. Он печатает полные данные для восстановления и завершается
с кодом возврата **2**:

```
ПОТЕРЯННЫЕ РУЧНЫЕ ПОЛЯ (1) — проставить заново:
  ! узла «raschet-potrebnosti-staryy-id» больше нет в презентации —
    потеряно screen «Расчёт потребности» https://inplan.company.ru/screens/demand
    (подпись: «Расчёт потребности на каждой локации»);
    возможно, это теперь raschet-potrebnosti-na-kazhdoy-lokacii-netting
```

Что делать: взять url и title из отчёта и проставить их на новый узел — либо через
редактор, либо правкой JSON. Подсказка «возможно, это теперь …» ищет узел с такой же
подписью и в случае переформулировки обычно попадает точно.

Файл при этом всё равно записывается: блокировать легальную правку презентации нельзя.
Ненулевой код возврата нужен, чтобы потерю нельзя было проскроллить в длинном отчёте.

## Ошибки и подводные камни

**Ссылка видна только мне.** Правки остались в `localStorage` и не выгружены. Экспорт →
файл в репозиторий → коммит.

**После `git checkout` файл «изменился» целиком.** В репозитории `core.autocrlf=true`
и нет `.gitattributes`, поэтому checkout может записать файл с CRLF и сломать побайтовое
совпадение с экспортом. Известная задача `process-map-61l`. Пока не исправлено — если
`git diff` показывает изменённым весь файл, проверьте окончания строк.

**Прогнали импорт, карта развалилась.** Забыли `npm run layout` следом. См. раздел выше.

**Ссылка не открывается на встроенной карте.** Скорее всего `sandbox` у `<iframe>`
в вики без `allow-top-navigation-by-user-activation` — браузер отказывает **молча**,
без ошибки. Подробности и способ проверки — в [README](../README.md), раздел
«Встраивание в In.Plan», условие 2.

**Ссылки на этапах.** Поле `stage.screen` в модели есть, но редактором **не правится** —
решением владельца проекта редактируются только ссылки узлов (`process-map-uml`).
Строка «Открыть в In.Plan →» на карточке этапа поэтому не появится.

кнопка «Открыть в модуле» становится активной.
